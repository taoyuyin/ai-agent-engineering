# Chapter 1 软件为什么需要 AI Agent？

Part I Foundations —— 为什么需要 AI Agent

Version: 2026-07

Last Updated: 2026-07-31

## Core Question

为什么今天会出现 AI Agent？

## Chapter Conclusion

AI Agent 的出现，并不是因为大语言模型突然“足够聪明”，而是因为软件正在面对越来越多无法被固定流程完整描述的开放性任务。

传统软件擅长执行预先定义好的流程。AI Agent 则代表一种新的软件执行范式：软件不再只是按照流程执行步骤，而是围绕目标，动态决定下一步行动。

一句话概括：

AI Agent 是软件从“执行流程”走向“完成目标”的一次范式变化。

## Learning Objectives

完成本章后，你应该能够理解：

- 为什么软件工程一直在解决复杂度问题
- 为什么传统软件擅长确定性任务
- 为什么开放性任务越来越难用固定流程描述
- LLM 给软件带来了什么新能力
- 为什么仅有 LLM 还不等于 Agent
- AI Agent 在软件工程中的位置

本章只讨论 Agent 为什么出现，不正式定义 Agent 的完整结构。Agent 的统一定义会在 Chapter 3 展开。

## 1.1 软件的发展，本质是在控制复杂度

软件工程的发展历史，本质上是一部持续控制复杂度的历史。

每一次重要的软件技术演进，背后几乎都对应着一个问题：

上一代软件组织方式，已经无法继续支撑新的复杂度。

例如：

| 阶段 | 主要问题 | 解决方式 |
|---|---|---|
| 汇编语言 | 开发效率低，难以维护 | 高级语言 |
| 结构化编程 | 控制流混乱 | 函数、模块、顺序、分支、循环 |
| 面向对象 | 大型系统复杂，状态难管理 | 封装、继承、多态 |
| MVC | 界面、业务、数据耦合 | 分层设计 |
| SOA | 企业系统之间难复用、难集成 | 服务化 |
| Microservice | 单体应用过大，团队协作困难 | 服务拆分、独立部署 |
| Cloud Native | 运维复杂，资源弹性不足 | 容器、编排、自动化运维 |

这些技术看起来方向不同，但共同目标是一致的：

降低复杂度，提高软件系统的可理解性、可维护性和可演进性。

软件工程不是在追求“更复杂的技术”，而是在寻找更适合当前问题规模的组织方式。

AI Agent 也是如此。

它不是凭空出现的新概念，而是在软件系统开始面对新一类复杂任务之后，自然产生的新执行方式。

## 1.2 传统软件擅长解决确定性问题

过去几十年的软件开发，大多建立在一个重要假设之上：

开发者能够提前定义系统的执行过程。

以订单系统为例，一个典型流程可以被提前设计为：

```text
创建订单
  ↓
校验库存
  ↓
计算价格
  ↓
生成支付单
  ↓
支付完成
  ↓
安排发货
```

在这个系统中，开发者需要提前定义：

- 有哪些步骤
- 步骤之间的顺序是什么
- 每一步需要哪些输入
- 什么条件下进入哪个分支
- 出错时如何处理
- 数据如何存储和传递
- 外部系统如何调用

这种模式非常强大。

它让软件可以稳定、可预测、可测试地运行。银行系统、订单系统、库存系统、ERP、CRM、数据仓库、报表平台，绝大多数企业软件都建立在这种确定性流程之上。

因此，传统软件的核心能力可以概括为：

将明确的业务规则，转换为可执行的程序流程。

只要业务规则足够清晰，执行路径足够确定，传统软件就是非常高效的解决方案。

问题在于，今天越来越多的软件需求已经不完全符合这个前提。

## 1.3 软件开始面对开放性任务

近年来，软件处理的问题发生了明显变化。

越来越多需求无法被提前完整写成固定流程。

例如：

- 总结一份几十页的技术文档
- 根据企业制度回答员工问题
- 分析销售额下降的原因
- 阅读合同并提取风险点
- 根据自然语言生成 SQL
- 自动阅读代码并修复错误
- 根据一组业务指标生成经营分析报告

这些任务与传统软件任务有明显不同。

第一，它们没有唯一固定流程。

例如“分析最近一个季度利润下降的原因”，这不是一个简单函数调用。不同公司、不同业务、不同数据结构、不同指标体系，都会导致完全不同的分析路径。

可能需要先看收入，也可能先看成本。可能需要分析产品线，也可能需要分析地区、客户、渠道、库存、折扣、退货、供应链。

也就是说，任务路径不是开发者预先完全写死的，而是在执行过程中逐步确定的。

第二，输入是开放的。

传统软件通常要求用户按照固定格式输入参数。但开放性任务中，用户往往直接表达目标：

```text
帮我分析最近一个季度利润下降的原因，并给出改进建议。
```

这句话不是传统意义上的结构化参数。它包含时间范围、指标对象、分析目标、输出要求，以及隐含的业务上下文。

第三，任务需要动态决策。

很多任务不是一次执行就结束，而是需要根据中间结果决定下一步。

```text
用户：分析销售额下降原因
  ↓
系统：查询销售数据
  ↓
观察：销售额下降主要集中在华东区
  ↓
下一步：继续分析华东区产品结构
  ↓
观察：某产品线销量下降明显
  ↓
下一步：查询库存、价格、促销、退货数据
```

这个过程不是固定流程。

它更像一个持续推理和探索的过程。

传统软件擅长“流程已知”的任务；开放性任务的难点在于，流程本身需要在运行时被决定。

## 1.4 LLM 给软件带来了新的能力

大语言模型的价值，并不只是生成自然语言。

对于软件工程而言，更重要的是：

LLM 让软件第一次具备了较强的自然语言理解和语义推理能力。

例如，用户输入：

```text
统计最近半年销售额下降最快的产品。
```

模型可以理解：

- “最近半年”是一个时间范围
- “销售额”是一个业务指标
- “下降最快”意味着需要比较变化幅度
- “产品”是分析维度
- 最终目标不是闲聊，而是完成一次数据分析任务

这意味着，软件系统可以开始理解用户用自然语言表达的目标。

在传统软件中，用户必须适应软件：点击菜单、填写表单、选择筛选条件、配置报表字段、编写 SQL、调用 API。

而在 LLM 之后，软件开始有能力适应用户：用户表达目标，系统理解目标，系统选择工具，系统组织执行过程，系统返回结果。

这并不意味着 LLM 替代了软件工程。

恰恰相反，LLM 只是给软件增加了一种新能力：

处理过去难以形式化描述的问题。

## 1.5 仅有 LLM，并不能完成复杂任务

如果把 LLM 看成一个文本生成器，那么它的基本模式是：

```text
Input
  ↓
LLM
  ↓
Output
```

这种模式适合回答问题、总结文本、翻译内容、生成草稿、改写表达、做一次性推理。

但真实的软件任务通常不是一次输入、一次输出就能完成。

例如生成一份销售分析报告，可能需要：

```text
理解用户目标
  ↓
查询数据库
  ↓
执行统计分析
  ↓
发现异常指标
  ↓
继续追问原因
  ↓
生成图表
  ↓
组织结论
  ↓
输出报告
```

这里不仅需要语言能力，还需要访问外部数据、调用工具、管理任务状态、记录中间结果、根据执行结果调整计划、判断任务是否完成，以及在失败时重试或请求人工介入。

这些能力已经超出了 LLM 本身的职责。

LLM 可以提供推理能力，但它不负责整个软件执行过程。

因此，仅有 LLM，不等于拥有一个 Agent。

一个只会回答问题的模型，不是 Agent。一个可以调用工具，但没有任务状态和执行循环的模型应用，也未必是 Agent。

Agent 的关键不只是“会说”，而是“能围绕目标持续行动”。

## 1.6 AI Agent 的出现

AI Agent 正是在这样的背景下出现的。

它不是一种新的模型，也不是某一个具体框架。

更准确地说，Agent 是一种新的软件组织方式。

它把 LLM、工具、记忆、上下文、状态和反馈组织在一起，让软件能够围绕目标持续执行任务。

```text
User Goal
  ↓
AI Agent
  ↓
Model / Tools / Memory / External Systems
  ↓
Result
```

在这个结构中，LLM 承担推理和决策能力。工具负责连接外部系统。Memory 负责保留任务相关信息。Agent Runtime 负责组织执行过程。

也就是说，Agent 的价值不在于替代 LLM，而在于组织 LLM。

LLM 是能力核心。Agent 是执行系统。

Agent 并没有取代传统软件系统。

它是在传统软件系统之上增加了一层新的执行能力。

## 1.7 从“执行流程”到“完成目标”

传统软件的核心是流程。

开发者提前定义：

```text
如果发生 A，执行 B；
如果满足 C，进入 D；
如果失败，执行 E。
```

而 Agent 的核心是目标。

开发者不再只定义完整流程，而是定义：

- 系统可以完成什么目标
- 系统可以使用哪些工具
- 系统可以访问哪些数据
- 系统必须遵守哪些约束
- 系统如何判断任务是否完成
- 系统什么时候必须停止或交还给人类

换句话说，开发者的工作重心发生了变化。

过去，开发者主要写的是执行路径。未来，开发者还需要设计的是执行边界。

传统软件问的是：

系统下一步应该执行哪段代码？

Agent 系统问的是：

为了完成这个目标，当前最合适的下一步是什么？

这就是从“执行流程”到“完成目标”的转变。

## Summary

传统软件建立在确定性流程之上。

它非常适合规则明确、边界清晰、执行路径可以提前定义的任务。

但今天的软件系统正在面对越来越多开放性任务。这些任务输入不固定、路径不确定、需要动态决策，并且往往依赖外部数据和工具。

LLM 带来了自然语言理解、语义推理和工具调用能力，让软件可以开始理解用户目标。但仅有 LLM 还不够，因为复杂任务需要状态管理、工具调用、上下文组织、反馈循环和执行控制。

AI Agent 正是在这样的背景下出现的。

它不是一种新的模型，而是一种新的软件执行范式。

它让软件从“按照流程执行”走向“围绕目标行动”。

本章结论：

AI Agent 的出现，是软件工程为了应对开放性任务复杂度而产生的必然结果。

## Notes

本章不对 Agent 做完整定义，只解释 Agent 为什么出现。

本章中使用的 Agent 视角偏工程化：Agent 是一种围绕目标组织 LLM、工具、状态和反馈的软件执行系统。

OpenAI、Anthropic、Google 等厂商对 Agent 的定义和边界存在差异。Chapter 3 会统一讨论这些定义，并给出本书采用的工程定义。
